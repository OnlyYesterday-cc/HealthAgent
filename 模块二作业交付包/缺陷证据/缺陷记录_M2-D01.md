# M2-D01 JWT业务主体缺少校验

状态：已复现，待本人复核与修复。建议严重程度：中；需结合实际令牌签发来源评估。2026-09-14由AI辅助发现与复现，记录归入陆京超负责范围，不认定为本人独立原创。

## 环境与前提

业务源码基线99fb397；新增测试尚在工作区时执行。Python 3.10.11、FastAPI 0.115.0、pytest 8.3.3、SQLite内存数据库。使用隔离测试密钥签名，构造签名合法但缺失或不合法的sub。普通客户端无法在没有签名密钥时生成这种令牌，当前服务正常签发的sub为用户ID字符串，因此这是异常令牌的健壮性问题，不是已证实的认证绕过。

## 复现与现象

在仓库根目录执行backend/.venv/Scripts/python.exe 模块二作业交付包/run_module2_tests.py。

|用例|操作|预期|实际|
|---|---|---|---|
|M2-TC-001|访问令牌sub=not-an-integer，读取/users/me|401|500，detail=internal server error|
|M2-TC-002|刷新令牌sub=not-an-integer，调用/auth/refresh|401|500，detail=internal server error|
|M2-TC-003|刷新令牌缺少sub，调用/auth/refresh|401|500，detail=internal server error|

以上路径均以/api/v1为前缀。同批M2-TC-004、005的过期令牌均返回401，通过检查。整体5条中3失败、2通过，脚本退出码1。

## 根因分析与下一批方案

代码检查显示api/deps.py在JWT解码后直接执行int(sub)，非数字字符串触发ValueError；api/v1/auth.py刷新接口直接读取data['sub']并执行int，缺失键或非数字字符串会触发KeyError或ValueError。这些操作不在解码异常捕获范围中，最终被全局异常处理映射为500。HTTP500已由测试观察；具体异常类型是依据当前源码的分析，本批没有伪称捕获了内部堆栈。

三条失败暂合并为同一缺陷：JWT业务主体校验不完整。下一批统一校验用户ID，针对缺失、格式异常和取值范围给出一致拒绝，保留有效令牌流程，避免简单捕获所有异常掩盖数据库故障。修复后重跑本5条、后续新增5条及模块一回归，并保留修复前日志。

本批没有修改业务源码，没有修复后证据，缺陷未关闭。
